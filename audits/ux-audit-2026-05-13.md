## 1. Résumé exécutif

L'application InfraFlowSculptor dispose d'un design system mature (6 vagues livrées) et d'un shell enterprise fonctionnel (sidebar + topbar + footer). Cependant, l'audit révèle **20 findings** de sévérité variable, regroupés en 5 axes :

| Axe | Findings | Sévérité dominante |
|-----|----------|--------------------|
| Navigation & sidebar | F-01 à F-04 | Haute |
| Topbar & header | F-05 à F-07 | Moyenne |
| Footer & légal | F-08 à F-09 | Haute |
| Architecture de l'information (génération, droits) | F-10 à F-16 | Haute / Critique |
| Accessibilité | F-17 à F-20 | Moyenne |

**Verdict global :** La sidebar est sous-exploitée, le footer est juridiquement insuffisant, la génération Bicep/Pipeline mélangée avec la configuration crée une confusion sémantique, et l'affichage des fichiers générés occulte le contenu de configuration. Ces problèmes impactent l'utilisabilité, la confiance professionnelle, et la conformité légale.

## 2. Méthodologie et benchmarks

### Outils de référence comparés

| Outil | Pertinence | Ce qu'on observe |
|-------|-----------|------------------|
| **SonarQube** | Outil d'analyse de code, contexte projet similaire | Sidebar contextuelle par projet (overview, issues, measures, code, activity), header avec projet+branche, footer avec version + liens légaux |
| **GitHub** | Plateforme de code, référence UX universelle | Navigation tabs par repository (Code, Issues, PR, Actions, Settings), sidebar contextuelle dans Issues/PR, footer riche (Terms, Privacy, Security, Status, Docs) |
| **Azure Portal** | Cloud management, même domaine métier | Navigation à gauche arborescente par ressource, breadcrumb structuré, blade pattern pour le détail, séparation claire Monitoring/Settings/Operations |
| **Terraform Cloud (HCP)** | IaC management, concurrent direct | Sidebar par workspace (Runs, States, Variables, Settings, Team Access), séparation claire entre config et exécution |
| **Vercel** | SaaS deployment, référence modern SaaS B2B | Navigation tabs par projet (Deployments, Analytics, Logs, Settings), footer minimal mais complet (Legal, Privacy, Terms) |
| **Pulumi Cloud** | IaC, concurrent direct | Sidebar avec stacks/projects, séparation nette entre définition et exécution, historique des runs |

### Principes UX évalués

1. **Séparation des préoccupations** — Configuration ≠ Exécution/Génération ≠ Résultat
2. **Navigation contextuelle** — Le menu s'adapte au contexte courant (projet ouvert, config active)
3. **Progressive disclosure** — L'information se révèle progressivement sans surcharger
4. **Wayfinding** — L'utilisateur sait toujours où il est et comment revenir
5. **Legal compliance** — Footer avec mentions légales, CGU, politique de confidentialité
6. **Accessibilité WCAG 2.1 AA** — Contraste, navigation clavier, ARIA, responsive

## 3. Findings — Problèmes identifiés

### F-01 — Sidebar statique et vide (Sévérité : HAUTE)

**Constat :** La sidebar contient 4 items fixes (Home, Projects, Settings, Docs) quel que soit le contexte. Quand l'utilisateur ouvre un projet ou une configuration, la sidebar reste identique — aucune information contextuelle n'apparaît.

**Benchmark :**
- **SonarQube** : la sidebar change complètement quand on entre dans un projet → Overview, Issues, Security Hotspots, Measures, Code, Activity, Administration
- **GitHub** : la sidebar d'un repository affiche les fichiers, et la navigation tabs change (Code, Issues, Pull Requests, Actions, etc.)
- **Terraform Cloud** : la sidebar d'un workspace montre Runs, States, Variables, Settings, Team Access
- **Azure Portal** : la navigation gauche d'une ressource affiche Overview, Activity log, Access control, Tags, Settings, Monitoring, etc.

**Impact :** L'utilisateur doit se repérer uniquement par les tabs horizontaux dans les pages de détail. La sidebar est du "wasted space" qui ne contribue pas à la navigation.

**Score d'utilité actuel :** 2/10 — seuls 4 liens globaux, pas de contexte projet.

---

### F-02 — Aucune navigation contextuelle par projet (Sévérité : HAUTE)

**Constat :** Quand l'utilisateur est sur `/projects/:id`, la sidebar ne montre rien du projet. Les tabs horizontaux (`Configurations`, `Environments`, `Naming`, `Members`, `Pipeline Variables`, `Settings`) sont le seul moyen de naviguer dans le projet. Il manque :
- Le nom du projet dans la sidebar
- Les sections du projet comme liens de premier niveau
- Les configs du projet listées comme sous-éléments navigables
- Un accès rapide aux ressources des resource groups

**Benchmark SonarQube :** En entrant dans un projet SonarQube, la sidebar affiche le nom du projet + sa branche + les sections (Overview, Issues, Security, Measures, Code, Activity). La topbar montre le breadcrumb et la sélection de branche. Les tabs horizontaux sont réservés pour un sous-niveau de détail.

**Impact :** Sur un projet avec 5+ configurations et 20+ ressources, l'utilisateur doit constamment naviguer par tabs et faire du back-button. Il ne peut pas voir d'un coup d'œil la structure de son projet.

---

### F-03 — Le lien "Docs" pointe vers un placeholder (Sévérité : MOYENNE)

**Constat :** La sidebar a un lien `Docs` qui route vers `/docs`, mais c'est marqué comme "placeholder" dans le code source (`// NOTE: route /docs is currently a placeholder`). L'utilisateur clique et ne trouve rien d'utile.

**Benchmark :** SonarQube, GitHub, Terraform Cloud → les liens Docs sont toujours des liens externes vers la documentation produit, jamais des routes internes vides.

**Impact :** Perte de confiance, frustration.

---

### F-04 — Sidebar : aucun accès rapide aux projets récents/favoris (Sévérité : MOYENNE)

**Constat :** La sidebar ne montre pas les projets récemment consultés ni les projets favoris. L'utilisateur doit systématiquement passer par Home → Favorites ou Projects → chercher.

**Benchmark :**
- **SonarQube** : la sidebar montre les projets récemment vus
- **GitHub** : la sidebar du dashboard montre les repositories récents
- **Azure Portal** : le menu Recent + Favorites est toujours accessible

**Impact :** Augmentation du nombre de clics pour atteindre un projet fréquent.

---

### F-05 — Topbar pauvre en informations (Sévérité : MOYENNE)

**Constat :** La topbar ne contient que : breadcrumb (quand disponible) + language switch + user card + logout. Il manque :
- Recherche globale (projets, configurations, ressources)
- Notifications / alertes (générations terminées, erreurs)
- Lien rapide vers la documentation
- Help / Support

**Benchmark :**
- **GitHub** : barre de recherche globale en position centrale, notifications bell, create (+) menu
- **SonarQube** : recherche globale, alertes qualité
- **Azure Portal** : searchbar centrale, notifications, cloud shell, settings, help
- **Vercel** : searchbar cmd+K, notifications, feedback

**Impact :** L'utilisateur n'a aucun moyen de chercher rapidement dans ses projets depuis n'importe quelle page.

---

### F-06 — Breadcrumb incomplet (Sévérité : BASSE)

**Constat :** Le breadcrumb est signal-driven via `PageContextService`, ce qui est bien. Cependant, dans la page resource-edit (`/config/:configId/resource/:resourceType/:resourceId`), le breadcrumb ne montre pas le chemin complet : `Home > Projects > Projet X > Config Y > Resource Group Z > Resource W`. Il manque le lien vers le projet parent et le resource group parent.

**Impact :** L'utilisateur perd le contexte hiérarchique en profondeur.

---

### F-07 — Topbar : pas de menu de création rapide (Sévérité : BASSE)

**Constat :** Pour créer un projet, il faut aller sur Home ou Projects. Il n'y a pas de bouton "+" global dans la topbar pour accéder rapidement aux actions de création.

**Benchmark :** GitHub a un "+" menu persistant dans le header (New repository, New gist, New organization, Import repository).

---

### F-08 — Footer juridiquement insuffisant (Sévérité : HAUTE)

**Constat :** Le footer actuel est un "status bar" de 28px contenant uniquement :
- Version (`v dev`)
- Environnement (`development`)
- Lien "Docs" (pointe vers `https://aspire.dev` — qui n'est même pas la doc du produit)

**Il manque :**
- **Mentions légales** (obligatoire en France / UE pour tout service en ligne)
- **Politique de confidentialité / Privacy Policy** (obligatoire RGPD)
- **Conditions Générales d'Utilisation (CGU / Terms of Service)**
- **Politique de cookies**
- **Copyright notice** (© 2026 InfraFlowSculptor)
- **Contact / Support**
- **Lien vers le status page**

**Benchmark :**
- **GitHub** : `© 2024 GitHub, Inc.` + Terms + Privacy + Security + Status + Docs + Contact + Manage cookies + Do not share my personal information
- **SonarQube** : `© SonarSource SA` + version + liens docs + community
- **Terraform Cloud** : Terms of Use + Security + Privacy + Trademark Policy + Accessibility
- **Vercel** : Legal + Privacy Policy + cookie preferences

**Impact juridique :** Non-conformité RGPD (absence de politique de confidentialité accessible), absence de mentions légales (obligation légale en France pour un service B2B SaaS). Un client enterprise refuserait de valider la conformité.

---

### F-09 — Le lien Docs du footer pointe vers aspire.dev (Sévérité : MOYENNE)

**Constat :** `docsUrl = 'https://aspire.dev'` dans le footer component. Aspire est l'orchestrateur, pas le produit. Le lien devrait pointer vers la documentation InfraFlowSculptor.

---

### F-10 — Génération Bicep/Pipeline mélangée avec la Configuration (Sévérité : CRITIQUE)

**Constat :** Dans `config-detail`, le bouton "Generate All" et le panneau de résultats de génération (Bicep + Pipeline) sont dans la même page que les onglets de configuration (Resource Groups, Tags, Naming Templates). Le panneau de génération apparaît **au-dessus** des tabs de configuration et les occulte.

**Problèmes sémantiques :**
1. **Mélange de préoccupations** : la configuration est une activité de *définition*, la génération est une activité d'*exécution*. Les mélanger dans la même vue crée une confusion sur ce que fait chaque zone.
2. **Obstruction visuelle** : quand le panneau de génération est ouvert, il pousse ou couvre les tabs de configuration. L'utilisateur qui veut modifier sa configuration après avoir généré doit d'abord fermer/réduire le panneau.
3. **Ambiguïté d'action** : le bouton "Generate All" est au niveau de la config, mais pour les projets MultiRepo, il déclenche une génération qui concerne l'ensemble du projet.

**Benchmark :**
- **Terraform Cloud** : sépare clairement Configuration (Variables, Settings) de Runs (History, Current run, Plan output). Les Runs ont leur propre section/onglet, jamais mélangés avec les Variables.
- **GitHub Actions** : le code est dans l'onglet Code, les exécutions sont dans l'onglet Actions. Jamais mélangés.
- **Azure DevOps** : Pipelines est un espace séparé de Repos. La définition du pipeline est dans Repos, l'exécution et les résultats sont dans Pipelines.
- **Pulumi Cloud** : Stacks liste les déploiements/runs séparément des Settings/Config.

**Impact :** Confusion utilisateur, perte de contexte de configuration, workflow interrompu.

---

### F-11 — Affichage grossier des fichiers générés (Sévérité : HAUTE)

**Constat :** Le `BicepFilePanelComponent` affiche les fichiers générés dans un panneau workspace/editor qui occupe une grande partie de l'écran. Quand il est ouvert dans config-detail, il pousse le contenu de configuration vers le bas et oblige l'utilisateur à scroller pour retrouver ses tabs de configuration.

**Problèmes :**
1. Le panneau de génération est **inline** dans le flux de la page, pas dans un panneau latéral ou un onglet dédié
2. L'arbre de fichiers + le viewer de code prennent beaucoup de place verticalement
3. Pas de mode "flottant" ou "dockable" comme dans un IDE
4. Le collapse/expand est au niveau du panneau entier, pas granulaire

**Benchmark :**
- **GitHub** : les fichiers de code sont dans leur propre page avec navigation par arbre à gauche
- **Azure Portal** : les templates ARM sont dans un blade séparé, pas inline
- **Terraform Cloud** : le plan output s'ouvre dans un run dédié avec sa propre page

---

### F-12 — Split Infra/Code : complexité cognitive élevée (Sévérité : MOYENNE)

**Constat :** Le `SplitGenerationSwitcherComponent` dans project-detail crée un système de tabs imbriqués : tabs de projet → tab Configurations → panneau de génération → tabs Infra/Code → sous-tabs Bicep/Pipeline/Bootstrap. C'est 3 niveaux de tabs.

**Benchmark :** Aucun outil de référence n'utilise plus de 2 niveaux de tabs. Azure Portal utilise un niveau de tabs + des sections scrollables. GitHub utilise des tabs + du contenu inline.

---

### F-13 — Gestion des droits dispersée (Sévérité : HAUTE)

**Constat :** La gestion des droits et permissions est répartie sur plusieurs endroits :
1. **Members** (tab dans project-detail) — gère les membres et rôles du projet (Owner/Editor/Viewer)
2. **Role Assignments** (dans resource-edit) — gère les rôles Azure (RBAC) sur les ressources
3. **PAT** (dans settings) — gère les tokens d'accès personnel
4. **Auth** (implicite via Entra ID) — pas de page de gestion visible

Il n'y a pas de vue unifiée "Access & Security" qui permette de comprendre d'un coup d'œil :
- Qui a accès à quoi
- Quels rôles Azure sont assignés
- Quel est l'état des tokens

**Benchmark :**
- **GitHub** : Settings > Access > Collaborators, Moderation, Manage access — tout sous le même toit
- **Azure Portal** : Access Control (IAM) est un blade unifié par ressource/subscription/resource group
- **Terraform Cloud** : Team Access est un tab dédié par workspace
- **SonarQube** : Administration > Security regroupe Users, Groups, Permissions

---

### F-14 — Aucun historique de génération (Sévérité : MOYENNE)

**Constat :** Il n'y a pas d'historique des générations passées. L'utilisateur peut générer du Bicep/Pipeline, mais une fois qu'il quitte la page ou regénère, les résultats précédents sont perdus. Il n'y a pas de notion de "runs" comme dans Terraform Cloud ou GitHub Actions.

**Benchmark :**
- **Terraform Cloud** : liste complète des Runs avec statut, date, durée, plan/apply output
- **GitHub Actions** : historique complet des workflow runs
- **Azure DevOps** : historique des pipeline runs

**Impact :** Pas de traçabilité, pas de comparaison entre générations.

---

### F-15 — Page Settings sous-exploitée (Sévérité : MOYENNE)

**Constat :** La page `/settings` ne contient actuellement que la gestion des PAT (Personal Access Tokens). C'est un espace sous-utilisé qui pourrait regrouper :
- Préférences utilisateur (thème, langue par défaut, timezone)
- Notifications
- Intégrations (webhooks, API keys)
- Organisation/workspace settings

**Benchmark :**
- **GitHub** : Settings est une page riche avec Appearance, Accessibility, Notifications, SSH keys, GPG keys, Applications, etc.
- **SonarQube** : Administration couvre Projects, Security, Configuration, Marketplace
- **Terraform Cloud** : Settings par organization + par workspace

---

### F-16 — Home/Dashboard : métriques insuffisantes (Sévérité : BASSE)

**Constat :** Le dashboard montre uniquement le nombre de projets, les favoris, et les éléments récents. Il manque :
- Nombre de configurations
- Nombre de ressources Azure gérées
- Dernière génération (date, statut)
- Alertes/diagnostics en cours
- Activité récente du workspace

**Benchmark :**
- **SonarQube** : dashboard avec quality gate status, coverage, duplications, security hotspots, bugs, code smells
- **Terraform Cloud** : workspace health, run status, drift detection alerts
- **Vercel** : deployments récents, analytics, errors

---

### F-17 — Accessibilité : skip navigation manquant (Sévérité : MOYENNE)

**Constat :** Il n'y a pas de lien "Skip to main content" en haut de page pour permettre aux utilisateurs de lecteurs d'écran de sauter la navigation.

**WCAG :** 2.4.1 Bypass Blocks (Level A)

---

### F-18 — Accessibilité : roles ARIA simulés sur des div (Sévérité : MOYENNE)

**Constat :** Le Sonar PR 327 a déjà identifié que `ds-table` et `ds-tree-view` simulent des rôles ARIA `table`/`tree` sur des `div`/composants custom, ce qui pose des problèmes d'accessibilité. Le fix recommandé est d'utiliser des sémantiques natives avec support clavier explicite.

**WCAG :** 4.1.2 Name, Role, Value (Level A)

---

### F-19 — Accessibilité : contraste insuffisant sur certains éléments (Sévérité : MOYENNE)

**Constat :** Malgré les 7 passes de fix dark-mode (memory 14-frontend-design-system.md), certains éléments restent problématiques :
- Les chips de compteur dans `SplitGenerationSwitcherComponent` (0.67rem text sur fond translucide)
- Les textes `--ifs-text-muted` sur certains fonds `--ifs-surface-1`
- Les breadcrumb separators et labels secondaires

**WCAG :** 1.4.3 Contrast (Minimum) (Level AA) — ratio minimum 4.5:1 pour le texte normal, 3:1 pour le texte large.

---

### F-20 — Accessibilité : pas de focus trap dans les panneaux de génération (Sévérité : BASSE)

**Constat :** Les panneaux de génération (inline dans la page) n'ont pas de focus trap. Un utilisateur au clavier peut tab dans le panneau de génération puis tab hors du panneau sans avertissement, ce qui crée une navigation confuse.

**WCAG :** 2.4.3 Focus Order (Level A)

## 4. Propositions de réorganisation

### Option A — Sidebar contextuelle (modèle SonarQube)

**Principe :** La sidebar change en fonction du contexte :
- **Mode global** (Home, Projects) : liens globaux + projets récents/favoris
- **Mode projet** (project-detail) : nom du projet + sections (Configs, Environments, Members, Naming, Variables, Generations, Settings)
- **Mode configuration** (config-detail) : nom de la config + sections (Resources, Tags, Naming, Generations)

**Avantages :**
- Navigation riche et contextuelle
- Cohérent avec SonarQube, Azure Portal, Terraform Cloud
- L'utilisateur voit toujours la structure de son contexte

**Inconvénients :**
- Complexité d'implémentation significative
- Transition d'état de la sidebar à gérer

### Option B — Tabs renforcés + sidebar enrichie (modèle GitHub)

**Principe :** Garder les tabs horizontaux pour les sous-sections, mais enrichir la sidebar avec :
- Projets récents/favoris
- Recherche rapide
- Accès aux settings du projet courant
- Séparer Génération dans un onglet/section dédiée

**Avantages :**
- Plus simple à implémenter
- Cohérent avec GitHub tabs pattern
- La sidebar reste un menu global enrichi

**Inconvénients :**
- Moins de guidance contextuelle que l'option A
- Les tabs horizontaux peuvent encore être surchargés

### Option C — Navigation hybride (modèle Azure Portal)

**Principe :** Sidebar globale + breadcrumb structuré + blade pattern pour les détails. Chaque ressource/config s'ouvre dans un panneau latéral (blade) plutôt que dans une page full-width.

**Avantages :**
- Pattern familier pour les utilisateurs Azure
- Permet de voir plusieurs niveaux simultanément

**Inconvénients :**
- Complexité d'implémentation très élevée
- Pas le modèle le plus courant dans les SaaS B2B modernes
- Surcharge visuelle possible

### 5.2 Séparation sémantique : Define / Generate / Manage

Le groupement en 3 catégories sémantiques résout F-10 :

| Catégorie | Responsabilité | Contenu |
|-----------|---------------|---------|
| **Define** | Définir l'infrastructure | Resource groups, resources, environments, naming, tags, variables |
| **Generate** | Exécuter la génération et voir les résultats | Generation board, Bicep output, Pipeline output, Bootstrap, historique |
| **Manage** | Gérer l'accès, les repos, les settings | Members, Git repos, Project/Config settings |

## 7. Accessibilité — Audit et corrections

### Checklist WCAG 2.1 AA

| Critère | Statut | Détail |

| 1.4.11 Non-text Contrast | ✅ OK | Les focus rings et borders sont visibles |
| 2.1.1 Keyboard | ⚠️ Partiel | Navigation clavier fonctionne dans la sidebar et les tabs, mais pas testé en profondeur dans les panneaux de génération |
| 2.4.1 Bypass Blocks | ❌ Manquant | Pas de "Skip to main content" |
| 2.4.3 Focus Order | ⚠️ Partiel | Ordre logique en général, mais les panneaux inline peuvent créer de la confusion |

## Glossaire

| Terme | Définition |
|-------|-----------|
| **Define** | Phase de définition de l'infrastructure (resources, environments, naming) |
| **Generate** | Phase d'exécution de la génération Bicep/Pipeline/Bootstrap |
| **Manage** | Phase de gestion des accès, repos, settings |
| **Blade** | Pattern Azure Portal : panneau latéral pour le détail |
| **Progressive disclosure** | Révéler l'information par étapes, pas tout d'un coup |
| **Wayfinding** | Capacité de l'utilisateur à s'orienter dans l'interface |
| **Skip navigation** | Lien invisible pour sauter au contenu principal (accessibilité) |
| **Focus trap** | Contrainte de focus clavier dans un conteneur (modal, panneau) |
